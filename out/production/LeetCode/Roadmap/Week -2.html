📘 Arrays — how they actually sit in memory

An array is a block of contiguous memory — every element sits right next to the previous one, so arr[i] is an O(1) jump straight to that memory slot (that's why arrays are so fast to read). The trade-off: inserting or deleting in the middle means shifting everything after it, which is O(n). This week is about getting comfortable moving things around inside an array in a single pass, without using extra arrays.

✏️ Quick check on arrays basics

If you swap arr[2] and arr[5] in an array, does the array's memory address change? (No — you're just swapping values at two existing slots, O(1) work.)
Why is deleting the first element of an array O(n) but deleting the last element O(1)? (Deleting the first forces every other element to shift left by one; deleting the last touches nothing else.)

Concept

📘 Concept needed: The Two-Pointer Technique

The two-pointer technique means using two index variables that move through an array (often at different speeds or from different directions) instead of using nested loops. Here you use a "slow" pointer (insertPos) that only moves when it finds a non-zero value, and a "fast" pointer (i) that checks every element. The slow pointer always points to "the next empty slot for a non-zero number" — so by the time the fast pointer finishes scanning, all non-zero numbers have been shifted to the front, in order, using only one pass and no extra array.

Why this matters: any time you'd normally think "shift elements over" or "compact an array", two pointers usually turn an O(n²) shifting approach into a clean O(n) one-pass approach.

Clarification questions

✏️ Quick check — can you answer these before moving on?

In the two-pointer idea for Move Zeroes, does the insertPos pointer ever move faster than i?
Reveal answer
No — insertPos always moves at the same speed or slower than i, since it only advances when a non-zero value is found. i always moves forward every iteration.
Why don't we need a second array to solve this problem?
Reveal answer
Because insertPos always points to a position at or before i, so writing nums[insertPos] = nums[i] never overwrites a value we still need to read later.

💡 Reveal approach — step by step (hints)

Approach

  1. Two-pointer idea: keep a pointer insertPos that tracks where the next non-zero number should go.
  2. Walk through the array once with pointer i. Whenever nums[i] != 0, place it at nums[insertPos] and increment insertPos.
  3. After the loop, insertPos marks where the zeroes should start — fill everything from insertPos to the end with 0.

Complexity

Time O(n) — one pass. Space O(1) — in-place, no extra array.
Reveal full Java solution 
public void moveZeroes(int[] nums) {
    int insertPos = 0;
    for (int i = 0; i < nums.length; i++) {
        if (nums[i] != 0) {
            nums[insertPos++] = nums[i];
        }
    }
    while (insertPos < nums.length) {
        nums[insertPos++] = 0;
    }
}

📘 Concept needed: Boyer-Moore Voting Algorithm

Before this trick, the obvious approach is: count every number's frequency with a HashMap (you already know this from Week 1), then find the one with count > n/2. That works, but uses O(n) extra space.

The Boyer-Moore Voting Algorithm does it in O(1) space using a clever "cancellation" idea: imagine every occurrence of the majority element as a "+1 vote" and every other number as a "-1 vote" against whatever the current candidate is. Keep a running candidate and a running count. If count drops to 0, pick a new candidate (the current number). If the current number matches the candidate, count++; otherwise, count--. Because the majority element appears more than half the time, it can never be fully "cancelled out" by the other elements combined — it always survives as the final candidate.

Clarification questions

✏️ Quick check — can you answer these before moving on?

If count reaches 0 partway through the array, what does the algorithm do next?
Reveal answer
It picks the current number as the new candidate and resets count to 1 (that current number counts as its own first vote).
Why can't a non-majority element 'survive' as the final candidate?
Reveal answer
Because it appears in fewer than half the positions, so there aren't enough occurrences of it to out-vote the true majority element across the whole array — the cancellations always favor whichever number appears more than n/2 times.

💡 Reveal approach — step by step (hints)

Approach

  1. Simple approach: use a HashMap to count occurrences of every number, then scan the map for the one with count > n/2. O(n) time, O(n) space.
  2. Smarter approach (Boyer-Moore Voting): keep a 'candidate' and a 'count'. If count is 0, pick the current number as candidate. If the current number matches candidate, count++; otherwise count--.
  3. Because the majority element appears more than half the time, it always survives this cancel-out process.

Complexity

HashMap way: O(n) time, O(n) space. Boyer-Moore: O(n) time, O(1) space.
Reveal full Java solution 
public int majorityElement(int[] nums) {
    int count = 0;
    Integer candidate = null;
    for (int num : nums) {
        if (count == 0) candidate = num;
        count += (num == candidate) ? 1 : -1;
    }
    return candidate;
}
💡 Start with the HashMap version if Boyer-Moore feels confusing — get it working, then come back and learn the O(1)-space trick.

📘 Concept needed: Kadane's Algorithm

Kadane's Algorithm answers a simple question at every position in the array: "should I extend the subarray I was already building, or should I start a brand new subarray from here?" You keep a running currentSum. At each element, you compare: is currentSum + nums[i] better, or is nums[i] alone (starting fresh) better? Whichever is bigger becomes the new currentSum. Separately, you track maxSum as the best currentSum you've seen across the whole scan — because the best subarray might have ended a few steps ago, not necessarily right at the end of the array.

This "extend or restart, decided at every step" logic is a small taste of dynamic programming thinking — you'll see this shape again a lot later in the roadmap.

Clarification questions

✏️ Quick check — can you answer these before moving on?

If currentSum becomes negative at some point, is it ever worth carrying that negative sum into the next element?
Reveal answer
No — a negative currentSum can only drag down the next sum, so it's always at least as good to restart from the next element alone. That's exactly why we take Math.max(nums[i], currentSum + nums[i]).
Why do we need a separate maxSum variable instead of just returning currentSum at the end?
Reveal answer
Because currentSum can shrink after passing the best subarray (e.g. if later numbers are very negative) — maxSum remembers the best value seen at any point, even if currentSum drops afterward.

💡 Reveal approach — step by step (hints)

Approach

  1. Brute force: try every subarray → O(n²) or O(n³). Too slow.
  2. Kadane's idea: as you walk the array, keep a running sum 'currentSum'. At each element, decide: is it better to extend the previous subarray, or start fresh from this element?
  3. currentSum = Math.max(nums[i], currentSum + nums[i]) — if adding the previous sum would make things worse than starting over, restart.
  4. Track maxSum as the best currentSum you've seen so far.

Complexity

Time O(n) — one pass. Space O(1).
Reveal full Java solution 
public int maxSubArray(int[] nums) {
    int currentSum = nums[0];
    int maxSum = nums[0];
    for (int i = 1; i < nums.length; i++) {
        currentSum = Math.max(nums[i], currentSum + nums[i]);
        maxSum = Math.max(maxSum, currentSum);
    }
    return maxSum;
}
